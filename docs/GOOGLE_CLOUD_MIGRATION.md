# Google Cloud migration plan / План за преместване в Google Cloud

**Status (2026-10-01): proposal and cost estimate only. Nothing has been provisioned or moved.** This is a specific target for the [deployment baseline](../DEPLOYMENT.md), not a claim that the repository is already portable or that one VM provides high availability. Production cutover, DNS changes and device endpoint changes require a separate decision after the gates below pass.

## English

### Pilot target and monthly cost

Start with one always-on Compute Engine **Tau T2A `t2a-standard-4`** (ARM64, 4 vCPU, 16 GiB) in **Netherlands `europe-west4`**, a 40 GiB `pd-balanced` boot disk, a separate 100 GiB `pd-balanced` data disk and one in-use external IPv4 address. The disk sizes are *planning allocations*, not current measured consumption or a two-year capacity promise. The separate data disk simplifies backup/restore and host replacement; it does not replace an off-host backup. T2A matches the current Compose `linux/arm64` pins, subject to testing every image and OS dependency. [Google's T2A specifications](https://docs.cloud.google.com/compute/docs/general-purpose-machines) and [region/zone matrix](https://docs.cloud.google.com/compute/docs/regions-zones) describe this machine and availability.

**Illustrative on-demand USD estimate, 730 running hours, prices checked 2026-10-01, before tax:**

| Item | Calculation | Monthly |
| --- | ---: | ---: |
| `t2a-standard-4` in `europe-west4` | 730 × $0.161776364/hour | $118.10 |
| 140 GiB zonal `pd-balanced` provisioned | 140 × 730 × $0.000150685/GiB-hour | $15.40 |
| One in-use external IPv4 | 730 × $0.005/hour | $3.65 |
| **Predictable subtotal** | | **$137.15** |

The VM rate is from [Google Cloud's regional VM price selector](https://cloud.google.com/products/compute/pricing/general-purpose); disk is from [disk pricing](https://cloud.google.com/compute/disks-image-pricing); IPv4 is from [VPC network pricing](https://cloud.google.com/vpc/network-pricing). The selector defaults to another region unless `Netherlands (europe-west4)` is chosen. Recalculate in the [Google Cloud Pricing Calculator](https://cloud.google.com/products/calculator) before purchase: prices, currency and actual month length can change. Stopping the VM stops compute billing but does **not** remove provisioned-disk charges; a reserved static IP can also remain billable. T2A has no sustained-use or committed-use discounts, so this is not a discounted or Spot estimate.

The subtotal **excludes** internet egress, snapshots/off-host backup storage and restore traffic, Cloud Logging/Monitoring above any allowances, DNS if moved to Cloud DNS, paid support, taxes, and any optional load balancer, VPN or second VM. Thus it is **not a capped monthly bill**. Establish a billing budget and alerts and measure traffic, database growth and backup sizes before giving a firm operating budget. A second always-on `t2a-standard-4` for high availability would add another VM and its storage/network costs; this single-VM pilot has a host/zone failure point. For an 8-vCPU/32-GiB `t2a-standard-8` with the same disks/IP, the same published hourly rate yields about **$255.24/month** before variable items. Do not size for 1,001 Sites from the current pilot snapshot alone.

### What migrates—and what does not

- The backend containers and persistent state: OpenRemote/Keycloak/Manager, GrideX API and workers, three database stores (OpenRemote PostgreSQL/Timescale measurements, GrideX PostgreSQL workflows, market TimescaleDB), MQTT broker and mTLS identities, protected public proxy and Grafana provisioning/state. Inventory and ownership remain **in OpenRemote**, not in a new cloud database registry. Preserve all organisation realms and verified subjects.
- The portal and Docusaurus documentation are separate projects; this plan does not silently move their current hosting. Their public API/auth/docs links, OIDC callbacks and help URLs must be checked if backend origins change.
- ROCK Pi, ESP32, local Ethernet, Site routers and safety/commissioning controls remain at Sites. Only an explicitly approved per-Site transport endpoint may change; keep MQTT mTLS identity/topic ACLs and the selected WireGuard-or-direct mode. No automatic control enablement or OTA.
- The current Mac and its private runtime are the rollback source until restored data and customer flows are proven on the new host. Do not treat Git as a data backup or copy private secrets into a synced folder.

### Work package before a cutover

1. **Inventory and capacity.** Freeze reviewed backend, portal, docs and Edge Git SHAs, active Compose overlays, image digests, DB/volume names and sizes, bind mounts, realm/client list, routes, certificates, MQTT ACLs and Site transport modes. Record 7-day CPU/RAM peaks, disk growth, I/O, egress and user concurrency. The prior Mac snapshot of roughly 2.7 GiB of running-container memory is *not* a peak-load or production capacity test.
2. **Cloud foundation.** Select project, billing budget/alerts, `europe-west4` zone with T2A quota, supported ARM64 Linux image, least-privilege operator access, firewall and DNS/certificate strategy. Keep databases, Docker control plane, Keycloak master/admin, Grafana and MQTT administration private. Expose only reviewed HTTPS routes and, for Sites using direct mode, the dedicated MQTT/TLS 8883 ingress with client-certificate and topic checks. Admin access must have a controlled private path; do not equate a hidden URL with security.
3. **Portable packaging.** Add and review a cloud-specific Compose profile/overlays rather than running `compose.mac.yml` unchanged. Replace Mac/Colima network names, host binds and UID/GID assumptions; pin/test ARM64 image digests. Produce a sanitised matrix of every required environment *key*, mount, port, network, volume and certificate. Preserve exactly one operator-maintained backend `.env` outside Git/sync, mode `0600`; deliver only each service's required secrets. Cloud secret delivery may protect that one file, not create competing configuration sources. Render the selected Compose configuration with placeholders and test from a clean host.
4. **Backup and isolated restore.** Take encrypted, consistent backups of all three databases and relevant service state, including Keycloak realm/client configuration, Manager storage, Grafana, MQTT ACL/cert material and the single private configuration. Keep backup encryption keys separately and test restore in an isolated project without sending customer traffic there. Restore the *same* OpenRemote Asset hierarchy and realm/Site bindings; no direct SQL provisioning or duplicate live inventory. Set backup cadence, retention, restore-point and recovery-time targets only after measuring data growth and obtaining approval.
5. **End-to-end acceptance.** Test API health, one- and two-realm customer isolation, platform-admin controls, protected Manager HTML/API/WebSocket, anonymous and cross-realm denial, login/refresh/logout/password recovery/invitations, Site/device provisioning in OpenRemote, real MQTT mTLS → worker → OpenRemote Timescale history, ROCK/ESP heartbeat, BG-only ENTSO-E collection, service grants and embedded Grafana, email, docs and portal routes. Verify backups restore after a restart. Keep control/commissioning locks closed. Capture actual external-browser evidence; local/VPN-only probes are not proof of public access.
6. **Controlled cutover and rollback.** After separate approval, choose a maintenance window, lower relevant DNS TTL ahead of time, take a final consistent backup, quiesce writers and MQTT ingestion to avoid split-brain/duplicate delivery, restore and reconcile the last delta, then switch only the reviewed proxy/DNS and approved Site endpoint(s). Preserve the old host read-only and recoverable. If a gate fails, stop new writers, restore prior DNS/endpoint and old single-writer path, reconcile messages and database changes, and verify customer sessions before declaring rollback. Never run both sides as independent writable authorities. Record revisions, timestamps, observed checks and operator decision in [HANDOFF](../HANDOFF.md).

**Open gates:** portable cloud Compose/configuration matrix; measured capacity and cost model; encrypted backup plus clean-room restore; multi-realm/transport security acceptance; rehearsed cutover/rollback. Until these pass, **do not claim clone-and-start portability or a production-ready migration**.

## Български

### Предложена машина и месечна цена

За първи етап: една постоянно работеща Compute Engine **Tau T2A `t2a-standard-4`** (ARM64, 4 vCPU, 16 GiB) в **Нидерландия `europe-west4`**, 40 GiB `pd-balanced` системен диск, отделен 100 GiB `pd-balanced` диск за данни и един използван публичен IPv4 адрес. Размерите на дисковете са *план*, не измерена заетост или гаранция за капацитет за две години. Отделният диск улеснява възстановяването, но не заменя архив извън машината. T2A съответства на текущите `linux/arm64` настройки в Compose само след проверка на всеки образ и зависимост. Виж [спецификацията на T2A](https://docs.cloud.google.com/compute/docs/general-purpose-machines) и [наличните зони](https://docs.cloud.google.com/compute/docs/regions-zones).

Източници: [регионалната цена на машината](https://cloud.google.com/products/compute/pricing/general-purpose), [цените на дисковете](https://cloud.google.com/compute/disks-image-pricing) и [цената на IPv4](https://cloud.google.com/vpc/network-pricing). В селектора избери `Netherlands (europe-west4)` — иначе се показва друг регион. Преди поръчка пресметни отново в [калкулатора на Google Cloud](https://cloud.google.com/products/calculator), защото цени, валута и брой часове се променят. Спирането на VM спира таксата за изчисления, но не премахва таксата за заделените дискове; запазен статичен IP също може да се таксува. T2A няма отстъпка за постоянна употреба или предварителен ангажимент; това не е цена за Spot машина.

В сумата **не влизат** изходящ интернет трафик, snapshots/архиви извън машината и възстановяване, допълнителни логове/наблюдение, DNS при преместване към Cloud DNS, платена поддръжка, данъци и незадължителни балансировчик, VPN или втора VM. Следователно **$137.15 не е таван на сметката**. Нужни са бюджет/известия и измерване на трафика, ръста на базите и архивите. Втора постоянно работеща машина за висока наличност има отделна цена; този пилот има единична точка на отказ на хост/зона. При `t2a-standard-8` (8 vCPU/32 GiB) със същите дискове/IP сметката е около **$255.24/месец** преди променливите разходи. Не оразмерявай 1001 Обекта по измерванията на сегашния тестов обект.

### Какво се мести и какво остава

- Преместват се backend контейнерите и постоянните данни: OpenRemote/Keycloak/Manager, GrideX API и workers, трите бази (OpenRemote PostgreSQL/Timescale измервания, GrideX PostgreSQL процеси, пазарна TimescaleDB), MQTT broker и mTLS идентичностите, защитеното публично proxy и Grafana настройките/състоянието. Инвентарът остава **в OpenRemote**; пазят се организационните realm-и и проверените идентичности.
- Порталът и Docusaurus документацията са отделни проекти; тук не се преместват мълчаливо. При промяна на backend адресите се проверяват API/auth/docs връзките, OIDC callbacks и помощта.
- ROCK Pi, ESP32, Ethernet, рутерите и защитите/commissioning остават на Обектите. Сменя се само изрично одобрен endpoint за избрания транспорт; пазят се MQTT mTLS, topic ACL и режимът WireGuard или директен MQTT. Без автоматично включване на команди или OTA.
- Mac и частният runtime остават за връщане назад, докато новият хост не докаже възстановени данни и работещи клиентски процеси. Git не е архив на данни; тайните не се копират в синхронизирана папка.

### Работа преди преместване на живо

1. **Опис и капацитет.** Запиши прегледаните Git ревизии на backend, портал, docs и Edge, активните Compose файлове, image digest-и, бази/volumes и размерите им, mounts, realm/client списък, маршрути, сертификати, MQTT ACL и транспорт по Обект. Измери 7-дневни пикове на CPU/RAM, ръст на диска, I/O, трафик и едновременни потребители. Предишната снимка от около 2.7 GiB памет на работещи контейнери **не** е пиково натоварване.
2. **Облачна основа.** Избери проект, бюджет/известия, зона в `europe-west4` с T2A квота, ARM64 Linux, минимални операторски права, firewall и план за DNS/сертификати. Базите, Docker управлението, Keycloak master/admin, Grafana и MQTT администрацията остават частни. Публикувай само проверените HTTPS пътища и за Обектите с директен режим — отделния MQTT/TLS порт 8883 с клиентски сертификати и права по теми. Админ достъпът е през контролиран частен път; скрит URL не е защита.
3. **Преносим пакет.** Добави и провери облачен Compose профил вместо да пускаш `compose.mac.yml` без промени. Замени Mac/Colima мрежи, пътища и UID/GID допускания; провери ARM64 образите. Направи обезличена матрица на всички конфигурационни *имена*, mounts, портове, мрежи, volumes и сертификати. Пази един поддържан backend `.env` извън Git/синхронизацията, с права `0600`; всяка услуга получава само нужните ѝ тайни. Облачна услуга за тайни може да доставя този файл, не да е втори независим източник. Провери Compose с примерни стойности от чист хост.
4. **Архив и изолирано възстановяване.** Направи криптирани съгласувани архиви на трите бази и нужното състояние: Keycloak realm/client настройки, Manager storage, Grafana, MQTT ACL/сертификати и единната частна конфигурация. Пази ключовете за архива отделно; докажи restore в изолиран проект без клиентски трафик. Възстанови същите OpenRemote Assets, realm-и и връзки, без директно SQL провизиране или дублиран инвентар. Честота/срок на архивите и целите за възстановяване се определят след измерване на ръста и одобрение.
5. **Приемателни тестове.** Провери API, изолация между два клиентски realm-а, глобален администратор, защитени Manager HTML/API/WebSocket, отказ към анонимни/чужди потребители, вход/refresh/изход/парола/покани, провизиране на Обект/устройство в OpenRemote, реален MQTT mTLS → worker → OpenRemote Timescale запис, ROCK/ESP heartbeat, BG-only ENTSO-E, права за услуги и вграден Grafana, имейл, docs и портал. Провери рестарт и възстановяване от архив. Управлението и commissioning остават заключени. Нужен е реален външен browser тест; локална/VPN проба сама не доказва публичен достъп.
6. **Контролирано превключване и връщане.** След отделно одобрение избери прозорец, намали DNS TTL предварително, направи последен съгласуван архив, спри приемането на нови записи/MQTT към стария източник, за да няма две паралелни системи, възстанови/съгласувай последните данни и смени само проверените proxy/DNS и одобрените endpoint-и на Обектите. Старият хост остава запазен и възстановим. При неуспех спри новите writers, върни DNS/endpoint и единствения стар път за запис, съгласувай съобщенията/данните и провери сесиите. Не оставяй две независими системи с права за запис. Запиши ревизии, часове, резултати и решението в [HANDOFF](../HANDOFF.md).

**Отворени условия:** облачен Compose и матрица на настройките; измерен капацитет/цена; криптиран архив и restore от чиста среда; многоорганизационни и транспортни тестове; упражнено превключване/връщане. Дотогава **не твърди, че сваляне на Git е достатъчно или че миграцията е готова за продукция**.
